# 自动计划/构建模式方案

## 背景

当前输入区只有“计划/构建”二态按钮：计划模式让 LLM 先输出方案，用户在计划审核弹窗中批准后再触发构建；构建模式直接执行用户请求。这个模型已经能覆盖一部分工作流，但存在两个问题：

1. 用户必须手动判断是否进入计划模式；对小修小补来说这很重，对大改动来说又容易漏掉计划。
2. “批准计划后进入构建”的链路还不是完整的一等流程，部分前端提交路径和后端状态持久化没有对齐。

目标是把模式语义收敛成三层：

- **自动**：默认入口，由 LLM/系统策略判断本轮是直接构建还是先计划。
- **计划**：用户明确要求先梳理方案，只产出可审核计划。
- **构建**：用户明确要求直接落实，除非遇到硬性安全边界或需求不清，否则不强制弹计划。

## 用户体验

输入区按钮最终应表达“自动/计划/构建”三个策略，而不是把“构建”当作计划模式的反面。

- 自动：普通默认状态。发送后系统先判定本轮有效模式；简单任务直接构建，大改动先进入计划审核。
- 计划：发送后只梳理方案，完成后弹出“计划审核”。
- 构建：发送后直接进入执行；仍保留工具授权弹窗、沙箱权限、问题澄清等安全机制。

计划审核弹窗是“从计划进入构建”的授权边界：

- 取消：丢弃待审计划，保持当前会话可继续输入。
- 编辑：用户可修改计划文本。
- 直接构建/批准执行：关闭计划模式，并发送“按已批准计划执行”的构建回合。

注意：批准计划不是工具授权。构建回合里如果需要执行命令、写文件、访问高风险路径，仍按现有权限系统弹 `tool_confirm`。

## 模式边界

### 可以直接构建

满足以下条件时，自动模式应直接走构建：

- 用户明确说“直接改”“修掉”“实现”“跑一下”“按这个做”。
- 小范围、局部、可回滚的变更，例如单文件样式、文案、字段校验、明显 bug 修复。
- 纯验证类请求，例如运行测试、构建、类型检查、查看日志、复现错误。
- 只读查询或解释，且不需要跨模块方案设计。
- 已经有明确方案/PRD/issue，当前请求只是按方案落地。

### 必须先计划

满足以下任一条件时，自动模式应切到计划：

- 跨模块或架构级改动，例如 agent 循环、工具派发、协议、持久化、前端状态机联动。
- 涉及数据库 schema、配置格式、用户数据目录、权限/沙箱、安全边界。
- 影响主交互流程或难以回滚的 UX 改动。
- 批量修改、删除、迁移、重命名等高影响操作。
- 需求含混且继续实现会产生明显方向风险。
- 用户明确说“梳理方案”“设计一下”“评估”“重构方案”“大改”。

### 灰区处理

灰区不应先弹正式计划。系统可以先做只读探索，读代码、查文档、定位影响面，然后再决定：

- 能收敛成局部修改：直接构建。
- 发现影响面扩大或存在不可逆风险：输出计划并等待用户批准。
- 缺少关键信息：用 `question` 或普通澄清问题向用户确认。

## 技术方案

### 后端模型

将 `plan_mode: boolean` 升级为更明确的策略字段：

```ts
type TurnModePolicy = 'auto' | 'plan' | 'build'
type EffectiveTurnMode = 'plan' | 'build'
```

兼容期内：

- `plan_mode=true` 映射为 `turn_mode_policy='plan'`。
- `plan_mode=false` 映射为 `turn_mode_policy='build'` 或旧版二态按钮语义。
- 新 UI 默认使用 `auto`，旧会话若没有该字段，则按旧 `plan_mode` 映射。

在 agent 层增加轻量 `TurnModeOrchestrator`：

1. 输入：用户消息、附件类型、会话 meta。
2. 输出：`TurnModeDecision{policy,effective_mode,reason,confidence,requires_plan_review}`。
3. 执行：
   - `effective_mode=build`：正常 `ChatWithTools`。
   - `effective_mode=plan`：进入计划工具白名单，并在结束时产生待审计划。

### 计划模式工具边界

计划模式需要拆成两个级别：

- **PlanTextOnly**：完全禁用执行工具，只输出方案。适合用户明确“只要方案”。
- **PlanExplore**：允许只读探索和 `todo_write`/`question`，禁用写文件、执行命令、子代理、媒体生成、外部写操作。适合自动模式判断前的灰区探索。

当前先保留文本计划为主；后续再增加 PlanExplore 白名单，避免一次修改过大。

### 前端状态

前端需要把“计划待审”作为阻塞态：

- 有 `pendingPlanText[sessionId]` 时，不自动 drain 队列。
- 批准计划时走统一的 `submitConversationTurn`，复用开始/结束流、断流恢复、取消、排队续跑。
- 批准前先把本地与服务端 `plan_mode` 都切回 false，防止构建回合结束又被捕获成新的待审计划。

### 持久化

后续版本建议为待审计划引入一等元数据：

- `plan_id`
- `status: pending | approved | cancelled | superseded`
- `source_message_id`
- `approved_text_hash`

第一阶段仍复用现有 `pendingPlanText` 前端状态和会话 `plan_mode`，但必须确保 `PATCH /sessions/:id` 能真正保存 `plan_mode`。

## 分阶段实施

### P0：修正现有链路

- `PATCH /api/v1/sessions/:id` 支持 `plan_mode`。
- 计划批准后不再重复插入一条相同 assistant 计划消息。
- `PlanReviewModal` 复用 `submitConversationTurn`。
- 队列 drain 遇到待审计划时暂停。
- 本地 `sessionMeta` 从服务端响应同步 `plan_mode`。

### P1：三态 UI 与协议兼容

- 新增 `turn_mode_policy`，保留 `plan_mode` 兼容。
- 输入区按钮改为 `自动/计划/构建`。
- 会话列表、创建会话、PATCH meta 都支持新字段。

### P2：自动模式决策器

- 增加 `TurnModeOrchestrator`。
- 先用确定性规则覆盖明显场景，再把 LLM 判断限制在灰区。
- 在 SSE `phase` 中暴露本轮决策结果，前端展示“自动选择：计划/构建”。

### P3：PlanExplore 工具白名单

- 将计划模式从“文本-only”扩展到“只读探索 + 计划”。
- 显式禁用写入、执行、外部副作用工具。
- 增加 agent 层单元测试覆盖工具白名单。

### P4：计划持久化与跨端支持

- 待审计划落库。
- CLI/HTTP/IM 使用同一套计划确认语义。
- 支持编辑计划后保存批准版本，并在构建回合引用批准版本。

## 当前实现范围

本次已落地：

- P0：`plan_mode` PATCH 持久化、计划批准链路复用统一提交、队列待审计划阻塞、避免重复写入计划。
- P1 第一版：新增 `turn_mode_policy=auto|plan|build`，前端按钮切换为自动/计划/构建三态。
- P2 第一版：自动模式先用确定性规则处理明确请求，再用 LLM 短 JSON 分类处理灰区；失败时降级为构建。

仍待后续独立推进：

- P3：PlanExplore 只读工具白名单。
- P4：待审计划落库、CLI/IM 的完整计划审批体验。
